# AI 功法创建与导入模型设计

文档状态：待确认草案
版本：v0.2
日期：2026-08-24

## 1. 文档目标

本文档用于确定“创建功法时，用户需要输入什么、AI 需要生成什么、系统如何把草案导入正式功法”的第一版模型。

本文档确认后，后续的 TypeScript 类型、mock 生成器、页面工作流、导入器和真实 AI 接口都应以此为基准。后续允许通过版本号继续调整，但不应在不同页面中各自定义一套输入输出格式。

## 2. 核心原则

1. AI 只生成可编辑草案，不直接修改正式功法、知识点或历史记录。
2. 生成过程分为“功法与大章结构生成”“大章单元生成”“单元知识点生成”三个阶段。
3. 用户先确认功法基本信息、规则建议和大章，再确认每个大章的单元，最后为每个单元设置知识点精细度。
4. AI 负责理解课程内容并提出结构、难度和任务建议；系统负责生成 id、时间、状态、进度和最终计算值。
5. 导入前必须先生成差异预览，用户确认后才一次性写入正式数据。
6. 草案知识点数量与正式功法不同时，不自动删除正式知识点。
7. 已经有关联修炼记录的正式知识点只能归档，不能因重新生成或导入而硬删除。
8. 第一版结构必须能够承载约 16 个大章、约 160 个单元和每单元不定数量知识点的大型功法。
9. 局部重新生成只保存当前大章或单元的新修订，不重复保存整门功法的全部内容。

## 3. 总体流程

```text
进入“创建功法”或已有功法的 AI 辅助入口
  -> 填写第一阶段必要信息
  -> AI 生成功法基本信息、规则建议和章节结构
  -> 用户修改并确认章节结构
  -> 用户为每个大章设置单元划分精细度
  -> AI 按大章生成单元草案
  -> 用户修改并确认单元结构
  -> 用户为每个单元设置知识点精细度
  -> AI 按单元生成知识点草案
  -> 用户编辑、增删或局部重新生成
  -> 系统计算数值并执行完整校验
  -> 展示导入差异和警告
  -> 用户确认导入
  -> 系统创建或合并正式功法数据
```

同一次创建项目可以产生多个组合版本。局部重新生成某个大章的单元时，只新增该大章的单元修订；局部重新生成某个单元的知识点时，只新增该单元的知识点修订。组合版本引用未变化的旧修订，避免为大型功法反复复制全部章节、单元和知识点。

## 4. 必填、补充和系统带入的定义

### 4.1 用户必填

没有该信息时，AI 无法稳定理解课程边界，或者系统无法决定草案应导入到哪里。用户必须填写、选择或明确接受默认值后才能进入下一阶段。

### 4.2 用户补充

没有该信息也能生成完整草案；填写后可以让结果更贴合用户当前水平、考试形式、时间安排和个人偏好。

### 4.3 系统带入

数据模型中必须存在，但不要求用户重复输入。例如从某个门派页面进入时，`sectId` 由当前 URL 和页面上下文自动带入。系统带入的字段仍应在界面上可见，以免用户在错误的门派或功法中生成草案。

## 5. 第一阶段：用户输入模型

第一阶段的目标是让 AI 生成“功法基本信息、基本规则建议和大章结构”，暂不生成单元和具体知识点。

### 5.1 必填内容

| 字段 | 输入方式 | 必填规则 | 作用 |
|---|---|---|---|
| 目标门派 | 页面带入或下拉选择 | 必须存在 | 决定功法所属领域，并选择对应的领域生成策略 |
| 功法名称 | 文本输入 | 必填 | 作为正式功法名称的初稿，也帮助 AI 判断课程主题 |
| 内容依据 | 文本、目录、考纲或材料解析文本 | 至少提供一种 | 限定 AI 应覆盖的内容，避免只凭课程名称自由发挥 |
| 学习目标 | 选择加文本说明 | 必填 | 说明是系统学习、考试准备、项目输出、能力训练还是自定义目标 |
| 目标层数 | 层数选择 | 必须存在，可接受系统默认值 | 决定课程需要规划到什么掌握深度，并影响规则和任务要求 |

“内容依据”采用组合必填规则。下列内容至少有一项不为空：

- 教材或课程说明。
- 教材目录或章节列表。
- 教学大纲或考试大纲。
- 用户自己描述的知识范围。
- 后续由文件上传功能解析出的正文或目录文本。

### 5.2 补充内容

| 字段 | 作用 | 未填写时的处理 |
|---|---|---|
| 当前基础 | 帮助 AI 控制解释起点和前置知识 | 按零基础或来源材料能够推断出的常规前置处理 |
| 学习周期 | 用于调整章节规模和阶段任务密度 | 只生成知识结构，不生成紧凑时间安排 |
| 每周可投入时间 | 用于提出更现实的训练量建议 | 不限制知识点数量，只提供常规任务要求 |
| 考试或成果形式 | 例如闭卷考试、论文、项目、口头讲解 | AI 按该门类的常规学习方式设计突破要求 |
| 重点内容 | 提高指定章节、能力或题型的重要度 | 按材料结构均衡处理 |
| 排除内容 | 明确不需要生成的范围 | 默认覆盖内容依据中的全部主要部分 |
| 参考功法 | 用于比较课程体量、难度和总值 | 使用当前门派的默认参考功法或全局基准 |
| 希望的修炼倾向 | 用户对法力、神识等收益倾向的偏好 | 由 AI 根据课程性质提出建议 |
| 补充要求 | 无法被结构化字段表达的特殊要求 | 不附加额外限制 |

### 5.3 系统带入内容

| 字段 | 来源 | 用户是否可以修改 |
|---|---|---|
| `targetMode` | 创建入口决定：`create_new` 或 `merge_existing` | 可以返回上一级切换入口，不在当前步骤直接修改 |
| `sectId` | 当前门派路由或用户选择 | 可以修改，但修改后需要重新生成 |
| `targetTechniqueId` | 从已有功法设置入口进入时带入 | 不允许改成另一个功法，应返回对应功法重新进入 |
| 全局数值规则 | 当前生效设置 | 在本流程中只读，可跳转到设置页调整 |
| 门派和参考功法信息 | 正式数据 | 在本流程中只读 |
| `schemaVersion` 和 `promptVersion` | 系统生成 | 不允许用户修改 |

## 6. 第一阶段：AI 必须生成的内容

### 6.1 功法基本信息草案

| 内容 | 是否必须 | 后续去向 |
|---|---|---|
| 功法名称 | 必须 | 映射到 `Technique.name` |
| 功法说明 | 必须 | 映射到 `Technique.description` |
| 课程体量与难度系数建议 | 必须 | 用户确认后映射到 `courseValueCoefficient` |
| 法力、神识、神魂收益倾向建议 | 必须 | 用户确认后映射到功法收益权重 |
| 最高规划层数 | 必须 | 映射到 `Technique.maxLayer` |
| 推荐前置功法 | 可以为空数组 | 系统匹配正式功法 id，用户确认后导入 |
| 生成依据说明 | 必须 | 只保存在草案生成信息中，不导入正式功法 |

AI 不得自行编造正式功法 id。推荐前置应先返回“名称、推荐理由和可选匹配提示”，由系统在已有功法中查找候选对象。

### 6.2 功法修炼默认规则草案

AI 必须为练习、笔记、思考、测试、复习五类修炼提出默认规则建议，包括：

- 各类型的最低经验要求比例或单位基础经验。
- 各类型的法力和神识收益权重。
- 新知识点默认练习数量。
- 新知识点默认笔记数量。
- 新知识点默认思考数量。
- 默认复习间隔和宽限比例。

这些内容都是建议值。用户可以修改，系统导入后形成该功法的 `TechniquePracticeDefaults`。

### 6.3 功法层数规则草案

AI 应按照目标层数生成每层规则建议：

- 累计功法经验门槛建议。
- 知识点覆盖比例。
- 核心知识点覆盖比例。
- 允许薄弱点比例。
- 突破要求标题、说明、类型以及是否为硬性要求。

层数经验门槛不能直接作为最终值。知识点生成完成后，系统需要根据知识点数量、有效价值和参考功法重新计算并提示校准。

### 6.4 章节结构草案

每个章节必须包含：

- 草案内部引用键，由系统在接收 AI 返回值后生成。
- 章节代码。
- 章节名称。
- 章节说明。
- 章节顺序。
- 本章学习目标。
- AI 推荐的单元划分精细度。
- AI 推荐的单元数量范围。

此时草案大章可以暂时没有单元，但正式数据必须补齐完整结构。`TechniqueChapter` 通过 `techniqueId` 归属功法，`TechniqueUnit` 通过 `chapterId` 归属大章，知识点只通过必填的 `unitId` 归属单元。需要直接服务整个大章的总结性知识点，应放入该章的“综合/总结”单元，不在知识点上重复保存章节和功法 id。

## 7. 第二阶段：大章单元生成模型

第二阶段以用户已经确认的大章为上游输入。单元是大章和知识点之间的正式结构，可以对应教材中的节、小节、主题模块或训练模块。

### 7.1 用户必填内容

| 字段 | 必填规则 | 说明 |
|---|---|---|
| 是否纳入本次生成 | 必须存在，默认开启 | 用户可以暂时跳过某个大章 |
| 单元划分精细度 | 必须存在，默认 `normal` | 可选 `rough`、`normal`、`detailed`、`custom` |
| 自定义单元数量 | 选择 `custom` 时必填 | 其他精细度下可以不填，由 AI 在推荐范围内决定 |

### 7.2 用户补充内容

| 字段 | 作用 |
|---|---|
| 目标单元数量 | 覆盖 AI 推荐的单元数量 |
| 本章重点 | 指定需要独立形成单元的理论、方法、人物、文本或能力 |
| 本章排除内容 | 避免生成超出课程范围的单元 |
| 单元组织要求 | 例如按教材小节、问题域、方法链或训练模块组织 |
| 本章额外要求 | 记录只对当前大章生效的自然语言要求 |

### 7.3 AI 必须生成的单元内容

每个单元草案至少包含：

- 所属大章草案引用键。
- 单元代码、名称、说明和顺序。
- 单元学习目标。
- AI 推荐的知识点精细度。
- AI 推荐的知识点数量范围。
- 单元结构的生成理由。

用户修改大章名称、顺序或说明后，第二阶段必须使用修改后的大章。单个大章可以独立生成和重新生成，不要求一次返回约 160 个单元。

## 8. 第三阶段：单元知识点生成模型

第三阶段以用户已经确认的单元为上游输入。每个准备生成知识点的单元都需要独立配置。

### 8.1 用户必填内容

| 字段 | 必填规则 | 说明 |
|---|---|---|
| 是否纳入本次生成 | 必须存在，默认开启 | 用户可以暂时跳过某个单元 |
| 知识点精细度 | 必须存在，默认 `normal` | 可选 `rough`、`normal`、`detailed`、`custom` |
| 自定义目标数量 | 选择 `custom` 时必填 | 其他精细度下可以不填，由 AI 在推荐范围内决定 |

### 8.2 用户补充内容

| 字段 | 作用 |
|---|---|
| 目标知识点数量 | 覆盖 AI 推荐数量 |
| 本单元重点 | 指定需要细分的概念、定理、方法、题型、文本或能力 |
| 本单元排除内容 | 避免知识点超出当前单元边界 |
| 知识点组织要求 | 例如按定义、定理、证明、方法、题型或应用组织 |
| 本单元额外要求 | 记录只对当前单元生效的自然语言要求 |

### 8.3 AI 必须生成的知识点内容

每个知识点草案至少包含：

| 内容 | 数据作用 |
|---|---|
| 所属章节引用键 | 连接已经确认的大章，AI 不生成正式 `chapterId` |
| 所属单元引用键 | 连接已经确认的单元，AI 不生成正式 `unitId` |
| 名称 | 映射到正式知识点名称 |
| 说明 | 描述该知识点在当前功法中的学习边界 |
| 精细度 | 记录当前知识点划分尺度 |
| 类型标签 | 例如概念、定理、方法、题型、文本、人物、能力或应用 |
| 学习视角 | 例如理解、证明、计算、应用、比较、批判、表达或创作 |
| 难度 | 用于系统计算推荐基础价值 |
| 重要度 | 用于系统计算推荐基础价值并识别核心知识点 |
| 目标层数 | 当前规划希望达到的层数 |
| 最高可修炼层数 | 该知识点允许达到的最高层数 |
| 练习要求建议 | 映射到知识点练习数量要求 |
| 笔记要求建议 | 映射到知识点笔记数量要求 |
| 思考要求建议 | 映射到知识点思考数量要求 |
| 复习间隔建议 | 默认继承功法规则，只有确有必要时才提出覆盖值 |
| 法力、神识权重建议 | 映射到知识点收益权重 |
| 推荐前置知识点 | 使用草案引用关系，导入时再映射正式 id |
| 生成理由 | 只供用户校验，不导入正式知识点核心字段 |

AI 可以提出知识点价值调整建议和理由，但不直接决定正式 `baseValue`。系统根据精细度、难度、重要度、目标层数、规则和参考功法计算推荐基础价值，用户可以在导入前手动覆盖。

## 9. AI 不应生成或修改的内容

下列字段由系统或正式历史数据负责：

- 正式功法、章节、单元、知识点和规则 id。
- `createdAt`、`updatedAt`、`archivedAt` 等生命周期字段。
- 当前层数、当前经验和功法当前总值。
- 知识点当前状态、当前进度和已经完成的任务数量。
- 最近修炼时间、最近复习时间、下次复习时间和退化状态。
- 修炼记录、事件记录、突破记录及其关联。
- 已有正式知识点的删除决定。

AI 返回这些字段时，输入输出校验器应忽略或拒绝，而不能直接写入正式数据。

## 10. 草案与局部版本模型

页面使用的完整草案物化视图为：

```text
TechniqueCreationDraft
  id
  projectId
  variantId
  requestId
  targetMode
  sectId
  targetTechniqueId（合并到已有功法时存在）
  stage
  userInput
  techniqueDraft
  practiceDefaultsDraft
  layerRuleDrafts[]
  chapterDrafts[]
    unitGenerationConfig
    unitDrafts[]
      knowledgeGenerationConfig
      knowledgePointDrafts[]
  generationMetadata
  validationIssues[]
  status
  createdAt
  updatedAt
```

建议的阶段状态：

```text
input_pending：第一阶段输入未完成
structure_ready：功法结构和章节已经生成
units_pending：等待配置或生成章节单元
units_ready：需要生成的章节单元已经就绪
knowledge_pending：等待配置或生成知识点
knowledge_ready：知识点已经生成，可以编辑
ready_to_import：校验通过，可以查看导入预览
imported：已经导入
archived：用户放弃或归档
```

`TechniqueCreationDraft` 是供页面编辑和导入器读取的完整视图，不代表每个版本都要完整复制保存。持久化层使用下列局部修订模型：

```text
TechniqueCreationProject
  input
  activeVariantId

TechniqueDraftVariant
  structureRevisionId
  chapterUnitRevisionIds: chapterDraftId -> revisionId
  unitKnowledgeRevisionIds: unitDraftId -> revisionId

TechniqueStructureRevision
  功法基本信息、规则和大章结构

ChapterUnitsRevision
  一个大章当前采用的单元列表

UnitKnowledgePointsRevision
  一个单元当前采用的知识点列表
```

例如只重新生成“数列极限 / 单调有界数列”单元的知识点时，系统只新增一条 `UnitKnowledgePointsRevision` 和一个新的 `TechniqueDraftVariant`。新组合版本继续引用其他大章、单元的旧修订，因此不会把数百或上千个知识点再次复制到 localStorage。

## 11. 导入模型

### 11.1 两种导入模式

`create_new`：创建新的正式功法，同时创建章节、单元、知识点、修炼默认规则和层数规则。

`merge_existing`：把草案内容合并到已有功法。该模式用于从正式功法设置页进入 AI 辅助功能。

### 11.2 导入前差异计划

系统先根据草案生成 `TechniqueImportPlan`，至少展示：

- 将创建或更新的功法字段。
- 将创建、更新、保留或归档的章节。
- 将创建、更新、保留或归档的单元。
- 将创建、更新、保留、跳过或归档的知识点。
- 将创建或覆盖的功法修炼规则。
- 将创建或覆盖的功法层数规则。
- 导入后的知识点数量、功法总值和参考功法差异。
- 阻止导入的错误和需要用户确认的警告。

### 11.3 单元或知识点数量不同的处理

1. 草案中新出现的单元或知识点默认标记为“创建”。
2. 能和正式对象明确匹配的草案对象，默认只更新结构性字段，是否更新数值规则由用户确认。
3. 正式功法中存在、草案中不存在的单元或知识点默认“保留”。
4. 导入不会因为草案数量变少而自动删除正式单元或知识点。
5. 用户主动移除且不存在关联记录的知识点可以硬删除；空单元可以硬删除。
6. 包含已有知识点或历史关联的单元只能归档；存在修炼记录、事件或其他历史关联的知识点也只能归档。
7. 不能只根据名称自动认定两个单元或知识点相同；系统可以提出匹配建议，但必须使用稳定 id 或由用户确认映射。

### 11.4 不允许覆盖的正式数据

合并导入时，只允许更新名称、说明、章节与单元归属、精细度、难度、重要度、任务要求、复习规则和收益权重等配置字段。不得覆盖已有经验、进度、复习历史、修炼记录和生命周期信息。

### 11.5 正式 id 与归属映射

正式门派、功法、章节、单元和知识点的 id 只标识实体身份，不编码名称或父级。新建功法的建议 id 由创建项目 id 生成；章节、单元和知识点的建议 id 分别由对应草案实体 id 生成。调整门派、功法、章节或单元归属时保持实体 id 不变。

正式归属采用单一直接外键链：

```text
Technique.sectId
TechniqueChapter.techniqueId
TechniqueUnit.chapterId
KnowledgePoint.unitId
```

当前归属不创建额外关系 id。移动操作另存 `OwnershipChangeRecord.id` 及调整前后路径快照。不同功法中分别创建的同名知识点具有不同 id；只有用户明确执行“移动”时保留原知识点 id，执行“复制”时必须创建新 id。旧静态实体 id 不因本次规则调整而重命名。

### 11.6 校验和写入顺序

```text
校验 AI JSON 结构
  -> 校验必填字段、数值范围、章节引用和单元引用
  -> 计算推荐基础价值、单元价值、章节价值和功法总值
  -> 查找已有章节、单元和知识点的候选匹配
  -> 生成导入差异计划
  -> 用户处理冲突和警告
  -> 用户确认
  -> 在内存中构造全部正式对象
  -> 一次性保存正式数据
  -> 保存导入记录
```

任一步骤失败都不应留下只导入一半的数据。导入记录需要保存草案 id、版本、导入时间、创建和更新的对象 id，以及用户做出的冲突选择，方便后续核对。

## 12. AI 接口边界

页面只依赖三个核心能力：

```text
generateTechniqueStructure(input)
  输入：第一阶段用户输入、当前规则、门派和参考功法信息
  输出：功法基本信息、规则建议、层数建议和大章结构

generateChapterUnits(input)
  输入：已经确认的大章和每章单元生成设置
  输出：指定大章下的单元草案

generateUnitKnowledgePoints(input)
  输入：已经确认的单元和每单元知识点生成设置
  输出：指定单元下的知识点草案
```

三个接口都必须支持局部范围参数。默认不要求 AI 在一次响应中返回约 160 个单元或整门功法的全部知识点。当前 `src/utils/aiGenerationClient.ts` 已定义 `AiGenerationRequest`、`AiGenerationResponse` 与异步 `AiGenerationClient.generate()` 合同；请求固定携带 `requestId`、`schemaVersion` 和 `stage`，响应固定区分 `success` 与 `failed`。浏览器端通过 `/api/ai/technique-draft/generate` 请求独立本机后端；当前供应商为 DeepSeek，真实模式由后端调用兼容接口并要求返回 JSON `draft`。`aiGenerationValidation.ts` 会在后端返回前和浏览器收到后两次校验阶段、请求 id、局部生成范围、知识点归属、数值、前置引用与循环依赖。校验失败统一返回 `invalid_ai_response`，不会进入草案修订。真实 AI 请求通过后端发送，前端不保存 API Key。

## 13. 领域补充输入

门派可以在通用输入模型之上追加领域字段，但不能改变通用输出主结构。

### 13.1 哲学门派补充项

- 主要人物、文本或哲学时期。
- 希望覆盖的问题域和比较关系。
- 是否侧重原著阅读、概念分析、论证重构、考试或写作。
- 指定考试题型、写作任务和阶段成果。

### 13.2 英语门派补充项

- 目标考试或目标能力。
- 当前水平。
- 材料类型。
- 正确率、速度和输出质量目标。
- 希望重点训练的听、说、读、写或翻译能力。

这些字段默认属于补充内容。只有用户选择了对应的专项生成模式后，其中直接决定生成结果的字段才转为条件必填。

## 14. 本版建议定档内容

以下内容建议在 v0.2 确认后固定，后续实现不得绕开：

1. 正式内容层级为“功法 -> 大章 -> 单元 -> 知识点”。
2. 生成过程分为功法与大章结构、章节单元、单元知识点三个阶段。
3. 第一阶段至少需要目标门派、功法名称、内容依据、学习目标和目标层数。
4. 第二阶段每章必须明确是否生成单元以及单元划分精细度；第三阶段每单元必须明确是否生成知识点以及知识点精细度。
5. 任一阶段选择自定义精细度时必须填写目标数量。
6. 草案以大章嵌套单元、单元嵌套知识点，不再使用扁平知识点数组作为核心结构。
7. AI 不生成正式 id、进度、历史状态和最终统计值。
8. AI 输出必须先经过系统计算、校验和导入预览。
9. 导入到已有功法时，不因草案缺少某个单元或知识点而自动删除正式数据。
10. 草案持久化按结构、章节单元和单元知识点保存局部修订，组合版本引用修订 id。
11. mock 和真实 AI 使用相同输入输出契约。

## 15. 暂不在本版定档的扩展

- 文件上传、PDF 解析和 OCR 的具体实现。
- 不同 AI 服务商和模型的选择。
- 自动生成长期事件和学习日历。
- 知识点拆分、合并后的历史记录迁移。
- 多个草案之间自动合并最佳结果。
- 完整知识图谱和跨功法知识点依赖。
- AI 自动判断正式知识点应被删除或归档。
- localStorage 超过实际容量后的 IndexedDB 迁移方案。

## 17. 输入字段显示与校验标准

所有输入字段必须从统一字段标准元数据读取说明。字段标准代码保存在 `src/data/aiDraftFieldStandards.ts`，页面通过 `FieldReference` 显示，不在不同页面重复编写互相矛盾的范围。

每个字段至少显示：

- 必填或可选状态。
- 数据格式、单位和硬性范围。
- 默认值、AI 建议值或继承来源。
- 该字段会影响的下游内容。
- 数值改变后可以计算时的结果预览。

可选数值留空表示继承系统或 AI 建议，不得静默转换为 `0`。百分比在界面显示为 `0%` 到 `100%`，模型统一保存为 `0` 到 `1`。超出硬性范围时阻止保存；超出建议范围但仍在硬性范围内时只提示警告。

当前定档的主要数值硬范围：

| 字段 | 硬范围 | 默认或参考 |
|---|---:|---|
| 目标层数、最高规划层数 | 1～6 | 系统学习建议 4～6 |
| 学习周期 | 1～260 周 | 常规建议 4～52 周 |
| 每周投入 | 0.5～80 小时 | 常规建议 2～20 小时 |
| 功法收益倾向 | 0～1 | 独立倾向，不强制总和为 1 |
| 课程体量系数 | 0.50～2.00 | 基准 1.00，建议 0.80～1.50 |
| 修炼要求比例 | 0～2 | 测试固定为 0 |
| 修炼类型收益权重 | 0～1 | 法力与神识建议总和为 1 |
| 测试单位基础经验 | 1～1000 | 默认 30 |
| 练习、笔记、思考次数 | 0～100、0～20、0～20 | 默认 10、2、2 |
| 复习宽限比例 | 0%～100% | 默认 20% |
| 大章目标单元数量 | 1～40 | 优先显示 AI 推荐范围 |
| 单元目标知识点数量 | 1～30 | 优先显示 AI 推荐范围 |
| 层数覆盖和薄弱点比例 | 0%～100% | 覆盖率随层数不降低，薄弱点上限不升高 |

草案完成度固定检查“基本信息、功法规则、大章结构、单元结构、知识点、完整校验”六项。只有六项全部完成且不存在阻断错误时，草案才允许进入 `ready_to_import`。当前第二阶段完成后，知识点项仍应显示待完成，不能提前把草案标记为可导入。

当前第三阶段已支持按单元 mock 生成、批量补齐、人工新增、编辑、删除、排序和前置依赖设置。人工修改通过 `UnitKnowledgePointsRevision` 保存为新的 `manual` 修订；删除知识点时同步清理当前单元内指向它的前置引用。保存前校验字段范围、归属、复习间隔、前置引用和循环依赖。

当前已经新增纯函数导入规划器、确认页和正式应用器。规划器会完整校验功法规则、大章、单元、知识点、数值范围和引用关系，根据创建项目 id 与各草案实体 id 生成不包含父级和名称的建议正式 id，并输出 `create`、`update`、`keep`、`skip`、`archive` 动作及字段级差异。错误会阻止导入，覆盖已有实体的动作和全部警告需要用户明确确认。应用器先计算正式结构、功法默认规则和层数规则的完整结果，再批量提交应用状态。功法规则页支持以数学分析层数锚点或手动总经验校准知识点基础价值；重分配默认保留手动调整，也可显式纳入手动调整项。正式知识点只写入直属 `unitId`，其余归属沿结构推导。应用顶层和修炼主链已经接入正式结构仓库；系统通过隐藏系统门派承载独立功法，通过隐藏系统功法承载秘术合集，并已实现功法和知识点迁移预览、仓库原子更新与归属历史记录。正式知识点编辑、删除和恢复页面已经实现，当前结构、修炼选择、进度和提醒会排除已删除项。真实模式已通过本机服务调用 DeepSeek 兼容接口，并与 mock 模式共用结构化请求、双层校验和草案修订合同；一次真实生成、经验重分配和正式导入已完成手工验证。导入计划进入 `applied` 后，系统保存草案项目/版本、计划 id、确认项、警告项、动作快照和草案到正式实体映射；预览页与刷新不会写入正式数据。下一步补充正式章节/单元编辑、导入记录查看和跨单元前置依赖选择。
